# Experimental protocol: direct weight writing, inspection, and repair

## 1. Operational definition

**Weight-space programming (WSP)** means choosing or modifying *numerical parameters* of a neural network in order to satisfy a behavioral specification. In the strictest track, the agent submits numeric arrays directly and may not execute a gradient-based optimizer, search over candidate weights, or emit training code. Architectural choices may be fixed by the benchmark or exposed as a separate independent variable. The benchmark itself may execute forward passes to score the submission.

A useful distinction: analytic construction of ReLU circuits and compilation from an exact symbolic formula **are legitimate WSP artifacts**, but they are a conventional baseline, not evidence of an emergent ability to reason about opaque high-dimensional weight tensors.

## 2. Independent variables: randomized factorial design

| Factor | Conditions | What is isolated |
|---|---|---|
| Feedback | blind (0 probes); budgeted (e.g., 1, 3, 10); open (unlimited validation) | Benefit of environment interaction |
| Explanation | required; forbidden; optional | Whether verbal justification improves or impairs actual parameter quality |
| Reasoning access | direct numeric output; scratchpad allowed; arbitrary Python analysis; fixed forward-pass quota | Role of explicit computation and tools |
| Architecture | fixed shallow MLP; fixed deep MLP; architecture selected by agent | Weights vs architectural/program search |
| Weights given | from scratch; partially initialized; corrupted trained network; model generated by another agent | Construction versus diagnosis/editing |
| Prompt view | natural-language specification; formal truth table; code; physical description | Dependency on task representation |
| Parameter budget | 10, 100, 1,000, 10,000+ | Scaling and sparse-edit behavior |
| Output format | explanation plus weights; weights only; patch only; diagnosis only | Information content of response |

**Important:** The repository currently enforces only feedback modes, explanation presence/absence, and counting rejected submissions as attempts. The other axes are planned study factors, not implemented tool restrictions. "Blind" means zero calls through the session's `probe`; a local participant can inspect the source code and test oracles, so no genuinely secret test set exists unless the evaluator sets `WSP_SEED_SALT` and keeps it from the participant. The salt changes the seeded test and OOD inputs; the oracles stay public.

## 3. Session lifecycle

1. **Freeze** task version, input semantics, output semantics, architecture constraints, objective, and allowed operations. Register expected baselines before seeing any candidate score.
2. **Assign condition** independently of the agent, ideally using a random seed and a trial ID.
3. **Prompt** with a precise contract and require a JSON artifact. No scripts, training loops, stochastic search or alternate hidden output channels in the direct-weight-only arm.
4. **Record** model name/version, prompts, context, latency, sampling parameters, tool permissions, all attempts, and candidate hash. An isolated environment must enforce no tool calls when requested.
5. **Validate candidate syntax and topology** before scoring. A parse failure is a failure, not a free resubmission, unless protocol says otherwise.
6. **Optionally probe** the validation split within the preassigned budget. Persist every probe even if incorrect, including the candidate hash.
7. **Finalize once** on test, OOD and boundary splits; report both performance and total attempts/compute. All failures count, including parser errors and timeout cases.
8. **Analyze** per-task success rate, bootstrap confidence intervals across independent *tasks/seeds*, sample efficiency, effect sizes, paired comparisons and calibration.

The session file is a reproducible log, **not a security boundary**. For actual hidden evaluation, store test data and seeds on a controlled service and offer only task specs, limited validation responses and one final score per immutable signed artifact. Use held-out *task families* to prevent memorized exact constructions from dominating.

## 4. Splits and metrics

- **Finite Boolean tasks:** validation is an incomplete subset; final test is the *entire* finite truth table. This is exhaustive correctness on a fixed domain, not IID generalization.
- **Real-valued tasks:** validation has 64 seeded samples within [-2,2] per dimension; test has 512 different seeded samples; OOD has 512 samples within [-10,10]; edge includes explicit exact boundaries or ties.
- **Binary:** sign of final scalar (`>0`) gives class 1, including output exactly zero as class 0.
- **Multiclass:** argmax with lowest-index tie-break; thermostat labels are [hold,cool,heat].
- **Regression:** passes when the largest absolute error is at most `1e-6`, which implies mean squared error `<= 1e-12`; both are reported. A bound on MSE alone would let a single test point be off by about 2.3e-5. The tolerance is stringent for these exactly representable toy functions.
- **Robustness:** record task score after quantization, independent additive weight noise and function-preserving parameter transformations.
- **Comparison:** pair final scores with weight-count, prompt tokens, time, validation probes and successful repairs per changed parameter.

No confidence interval over the 512 samples should be construed as uncertainty across different *task classes*. Random seeds alone do not make these independent scientific discoveries.

## 5. Baselines and ablations

Use at least: (a) random weights of the same network shape (implemented), (b) symbolic exact synthesis or hand-coded circuits (implemented for ten examples), (c) gradient-trained network of identical architecture/budget (future), (d) black-box zeroth-order search with equal forward-pass quota (future), (e) conventional code generation and compilation to a neural circuit (future), (f) LLM prompted for code rather than weights (future).

For repair, compare random single-parameter edits, sign changes, magnitude sweeps, gradient-based local updates and a properly trained alternative under matched evaluation budgets. **A sparse edit that fixes a deliberately introduced error does not establish repair ability on real trained systems.**

## 6. Pre-registered acceptance criteria for next phase

- At least 20 *new* tasks per difficulty stratum, not drawn from the examples or prompts.
- At least 5 independent generations per model/condition/task; report failures and invalid JSON rates.
- Compare direct WSP to deterministic symbolic baseline and gradient training under compute/time budgets; preregister a primary metric.
- Hold out both numeric input sets and at least one problem family.
- Conclude that WSP adds value only if it wins on a meaningful metric **and** the result survives matched-baseline, selection-bias and contamination controls.

## 7. Example model instructions

### Blind, weights only

> You are given input and output semantics, a fixed network topology and activation functions. Return only a JSON candidate containing literal finite numerical weights and biases matching schema version 1. You may not train, run code, use optimizers, query an evaluator or obtain environment feedback. One submission only.

### Feedback-limited, explanation required

> Propose a numeric network that implements the task. Explain the function computed by each layer and why the output satisfies the specification. You may request at most three validation calls, each on the current candidate. Then submit your final complete weight arrays. Training and gradient descent are prohibited.

### Sparse diagnosis/repair

> Here is the full numerical parameter artifact, the input semantics and a failure trace. Identify which parameter(s) plausibly cause the defect; provide only explicit before/after scalar weight edits in a machine-readable patch. Avoid reconstructing or retraining the model. Your budget is at most K edited parameters and B observed forward passes.

### Weight interpretation, no running

> All model instances share identical architecture, input encoding and output labels. You receive only anonymous weight matrices. Predict the task each network performs and identify the reasoning circuit. You may not execute the network or inspect outputs. The evaluator will reveal behavior only after the prediction is locked.

Separate prompt scripts for tasks are intentionally not hard-coded into the evaluator: the runner must not know whether the candidate was produced by a human, this assistant, another LLM, or a compiler.

## 8. Known threats to validity

1. **Task leakage:** the generator/oracles/weights and task names are publicly readable. The system is a development benchmark, not a sealed scientific comparison.
2. **Architecture leakage:** even without task labels, different topologies can identify which task was intended. Weight reading must use identical topologies across candidate classes.
3. **Post-hoc selection:** choosing among many attempts after test feedback invalidates one-shot or zero-feedback claims.
4. **Deterministic analytic solutions:** all current positives can be derived from formulas; they neither require a general learning system nor prove an LLM discovered anything beyond established elementary constructions.
5. **Distribution shift:** OOD numbers are still from a finite, simple, specified range, not arbitrary real numbers. Analytical identities establish exactness more broadly only when their derivation is valid.
6. **Floating point and boundary conditions:** very small perturbations around zero margins can flip strict decision thresholds. Random test accuracy can conceal these issues.
7. **Computational budget confounding:** a tool-enabled agent may run Python and search. Compare against algorithms with equal compute budgets and verify no prohibited tool use.
8. **Inference of author skill:** successful examples do not establish a distribution of human or AI capabilities. Repeat with independent agents, fresh tasks and locked prompts.

## 9. Provenance and reproducibility

The baseline records in `results/` were generated using deterministic Python code in this repository. No gradient steps were used. The directly specified values in `examples/` and `fixtures/` were written by ChatGPT 6 with high reasoning, in a chat session on a ChatGPT Plus plan, and then executed and tested locally; [ROADMAP.md](ROADMAP.md#provenance-of-the-existing-artifacts) records what else is and isn't known. They are not registered blind trials, and a label such as `method=direct_weights` is **self-reported provenance**, not cryptographic proof. The randomly seeded controls and task oracles are open source by design.
